# WiFi Calling 版本选择与最小实机验证

新部署、美国线路或需要核实 UDP 500/4500 出口时，优先考虑英国德国美国统一版。已有旧版实测稳定的 UK／DE 场景可以继续保留，不必仅因版本号迁移。选择依据是脚本的控制方式与验证能力，不是对运营商、节点或 IMS 可用性的承诺。

本文适用于手机流量经过 Sparkle／Mihomo 的场景；三份 JavaScript 文件都是完整覆写，不能串联使用，也不是 iOS 代理软件的原生规则。ePDG 是手机连接运营商网络的接入网关；IMS 是承载运营商语音、短信等业务的 IP 多媒体子系统。

核对日期：2026-11-10。脚本与检查器基线为提交 [`43a16af`](https://github.com/alieismy/proxy-rules/tree/43a16afb62a22171ccf8e72ec66a9fcd1a1a0dba)。更新脚本、核心、节点或手机网络路径后，需要重新核对相关结论。

## 1. 选择哪个版本

| 版本 | 建议用途 | 影响选择的行为 |
| --- | --- | --- |
| [英国全网版 v16.1](../scenarios/wifi-calling/uk.js) | 保留或复现已有 UK／Vodafone DE 固定地址场景 | UK／Vodafone DE 电话组首项分别为自动 UK／DE；自动注入 Vodafone DE 三个固定地址及 IP 规则。没有 `OFF` 开关，也没有统一版的 UDP 500/4500 专用接管规则。固定地址当前是否可用，仍须实测 |
| [英国德国版 v16.1](../scenarios/wifi-calling/uk-de.js) | 已有稳定 UK／DE 场景，需要域名分流并保留普通德国 ePDG 默认直连 | UK／Vodafone DE 电话组首项分别为自动 UK／DE；普通 DE 组首项为 `DIRECT`；固定地址回退默认关闭。没有统一版的端口一致性与相邻拒绝保护 |
| [英国德国美国统一版 v16.9](../scenarios/wifi-calling/uk-de-us.js) | 新部署、美国线路，或需要按 profile、源地址和固定节点进行受控验证 | 默认 `OFF`，脚本列出的 ePDG DNS 与域名规则使用 `DIRECT`，不生成 UDP 500/4500 接管规则。四个代理 profile 分别使用对应的专用手动候选组，组首项为 `REJECT` |

表中的首项是生成配置顺序，不等于当前实际选择。脚本启用了 `store-selected`，历史选择可能继续生效。旧版电话组保留的 `DIRECT` 候选，以及英国德国版普通 DE 组的默认直连，都不是空组保护失效。

统一版处于 `OFF` 时，仅在界面选择一个 UK／US 节点，不会启用对应 profile，也不会生成端口规则。`OFF` 不停用通用覆写，不清除输入配置已有的 hosts。它也不表示所有未知目的地址都被强制直连，应以最终命中的规则为准。

三版当前行为以各自源码为准；通用修复与未调整的 App Store、Oracle、漏网之鱼策略见 [README](../README.md)。脚本内的运营商政策、历史 DNS 观测和旧客户端适用版本是历史记录，本文不将其重新认定为当前业务可用性证明。

## 2. 已验证与待验证的边界

| 证据层级 | 已有证据 | 仍不能证明的内容 |
| --- | --- | --- |
| 仓库配置生成 | `node scripts/check.cjs` 检查六份脚本、规则引用与默认行为；统一版覆盖 8 个活动 profile × 2 种源地址范围，并核对独立预期与代表 ePDG 路由／DNS | 客户端已经加载这些配置、所有节点命名都正确、真实连接按预期转发 |
| 核心解析与隔离运行 | 2026-11-10 使用 Mihomo v1.19.33：三份完整配置通过 `-t`；9 次隔离运行验证 72 个自动组；后续复核全部 216 个策略组读回，包括 144 个手动组。相关生成配置与脚本基线一致 | 当前客户端、实际订阅、节点 UDP 和运营商接入可用 |
| 手机流量与远端通路 | **待实机验证**：手机实际经过哪个核心、源地址、命中规则、最终节点、UDP 双向流量 | 仅有节点名称、HTTPS 测速、`udp: true` 或发送计数不能证明通路可用 |
| IMS 与业务 | **待实机验证**：目标 SIM 的 WLAN／IWLAN 注册或 WiFi Calling 状态，以及呼入、呼出、SMS 收发 | IKE 请求、UDP 4500 保活、IPsec 隧道活动不能单独证明 IMS 注册及业务成功 |

上述原生运行关闭了 TUN、DNS 和代理监听，使用测试节点及本机检查地址；完整配置解析使用已有公开规则缓存，没有验证外部规则新鲜度。原生夹具与日志未随仓库发布，`scripts/check.cjs` 仅重跑仓库检查，不重跑这些核心实验。Mihomo v1.19.33 是实际测试版本，不是本文声明的最低支持版本。

## 3. 测试前先确定边界

先执行下文的只读核对。后续实测中的切换 profile、选择节点、重新连接手机 Wi-Fi 或启用飞行模式，都是待安排的操作，不表示本文发布时已执行。

受控实测前，保存当前覆写、实际生成配置和策略组选择。一次只测一张 SIM、一个活动 profile、一个固定节点；需要修改常量时只改私人测试副本，重新应用后检查最终配置，不修改公开脚本。测试窗口内避免并发使用其他 IKEv2/IPsec 业务；该源地址的 UDP 500/4500 都可能被接管。

如果保持现有配置不变，而统一版仍为 `OFF`，只能核对默认行为，不能验收代理 profile 的端口保护。如果没有自然空组，也不能声称本机触发过空组回退。

## 4. 最小实机验证步骤

### 步骤一：确认手机流量经过目标核心

记录客户端与实际核心版本、脚本版本／提交、目标 SIM、当前 profile、电话组实际选择，以及手机到核心的网络路径。电脑开启系统代理或手机连上 Windows 热点，都不能单独证明手机 UDP 已进入 Mihomo。

通过客户端连接详情或手机侧入口抓包，把手机流量与该 Mihomo 实例对应起来。统一版使用 `SOURCE_IPS_REQUIRED` 时，以规则引擎实际观察到的源 IPv4 为准，不直接照抄热点 DHCP 地址。

如果源地址被转换成共享地址，就还不能证明单手机隔离；`198.18.0.0/15` 地址会被脚本拒绝作为这种隔离依据。不要为绕过检查直接使用 `ALL_TUN_CLIENTS`，它会扩大到全部 TUN 客户端。当前规则使用 IPv4 `/32` 限定源地址，不能据此认定手机其他路径或 IPv6 流量也已受控。

**通过依据：** 能将目标手机、实际入站类型、源地址和核心连接对应起来。没有看到记录时先检查路径和可见性，不直接认定流量不存在。三份脚本默认日志级别为 `warning`，没有成功连接日志并不表示没有连接；优先使用已有连接面板，必要时在另行安排的测试窗口增加可观测性。

### 步骤二：确认空组保护

在实际加载的配置中检查每份脚本的 8 个自动组：Global、TW、JP、SG、US、DE、UK、其他。每组都应有：

```yaml
empty-fallback: REJECT
```

再查看客户端策略组详情，或已有本地控制接口的只读 `/proxies` 结果，不为本测试另开公网控制接口。若某自动组自然没有符合条件的节点，Mihomo v1.19.33 的预期读回片段为：

```json
{
  "all": ["REJECT"],
  "now": "REJECT",
  "emptyFallback": "REJECT"
}
```

这是预期示例，不是手机实测记录。判据是实际唯一候选和当前目标均为 `REJECT`，没有退到 `COMPATIBLE` 或 `DIRECT`。官方将 `empty-fallback` 定义为组为空时使用的代理，默认值为 `COMPATIBLE`。[Mihomo 策略组文档](https://wiki.metacubex.one/en/config/proxy-groups/#empty-fallback)

若没有自然空组，记为“空组配置已核对，实际分支未触发”。补测可在独立临时配置中使用全部被过滤的测试节点，关闭 TUN、DNS 和代理监听，使用独立控制接口及数据目录，避免干扰当前核心；不要删除真实订阅来制造空组。

**通过依据：** 配置项与实际空组读回同时符合预期。手动选择 `REJECT` 只验证拒绝路径，不能代替空组回退测试；“所有节点测速失败”也不等于“没有候选”。其余手动组由固定成员避免空组，统一版四个 VoWiFi 手动组保留显式 `REJECT`，但仍需核对当前选择。

### 步骤三：确认 UDP 500/4500 分流

建议用统一版验证这一项。受控启用代理 profile 时，先明确目标国家、真实源地址和待验证的具体节点；不要让自动测速选择在测试中改变出口。若节点尚无 VoWiFi 成功记录，将其视为实验候选，不能因名称、HTTPS 测速或 UDP 标志先判定可用。

控制入口是 `VOWIFI_ACTIVE_PROFILE`：`UK`、`DE`、`VODAFONE_DE`、`US` 各有 `_DIRECT` 和 `_PROXY` 两种取值。默认 `VOWIFI_IKE_SCOPE = "SOURCE_IPS_REQUIRED"`，非 `OFF` profile 必须在 `VOWIFI_OBSERVED_SOURCE_IPV4S` 填入实际观察到的源 IPv4，否则配置生成会报错。只在准备好的私人测试副本中调整，重新应用后再核对下表；代理 profile 还须在对应 VoWiFi 组明确选择本轮具体节点并确认实际选择，不能停留在 `REJECT`。界面切换组选择不等于修改这些常量。

| 统一版模式 | 实际生成配置应有的行为 |
| --- | --- |
| `OFF` | 没有专用 UDP 500/4500 接管规则 |
| `*_DIRECT` | 两个目标端口进入 `DIRECT`，受设定的 TUN／源地址条件约束 |
| `*_PROXY` | 每个端口的主规则进入对应 VoWiFi 手动组，后面紧跟同条件 `REJECT`；端口规则位于一般域名分流之前 |

同时检查当前国家代表 ePDG 的域名路由与 DNS 目标，确认它们跟随同一 profile；未激活国家保持脚本设定的直连。DNS 策略作用于整份配置，不受端口规则的源地址条件限制。

核对手机实际查询的 ePDG 及别名是否在 `fake-ip-filter` 排除范围，供 IKE 使用的是实际地址而非 fake-IP。查不到实际地址或只拿到 fake-IP 时，先定位 DNS，不能把后续端口超时直接归因于代理节点。

相邻拒绝规则用于防止主规则选中不支持 UDP 的代理后继续落入其他分流。Mihomo 官方说明：UDP 请求匹配到不支持 UDP 的代理时会继续向下匹配。它不能检测节点宣称支持 UDP 后的上游静默丢包。[Mihomo 规则优先级](https://wiki.metacubex.one/en/config/rules/#priority)

重新建立手机的 WiFi Calling 连接后，核对连接详情：

1. 入站是否为 `TUN`，源地址是否符合规则，协议是否为 UDP。
2. 目标端口 500 或 4500 命中了哪条规则、哪个电话组，以及最终哪个具体节点。
3. 如果两个端口都出现，是否进入同一具体出口；代理 profile 是否意外落到 `DIRECT` 或通用兜底。
4. 是否有响应或双向流量，而不只是发送计数增长、超时和重复重传。

若短暂 UDP 记录无法从连接面板保留，可在手机侧入口使用已有抓包工具，Wireshark 显示过滤器为：

```text
udp.port == 500 || udp.port == 4500
```

IKE 可以直接从 4500 开始，因此没捕获到 500 不能单独判定失败；只观察到 4500 时，将 500 标为“本轮未观察”，不要写成两个端口均已实测。[RFC 7296 §2.23](https://datatracker.ietf.org/doc/html/rfc7296#section-2.23)

代理封装后，电脑物理网卡可能只显示代理服务器地址和端口；不能要求它仍出现明文 ePDG UDP 4500。入口抓包、核心连接链与手机状态需要按同一时间窗口对应。

**通过依据：** 已观察端口的真实连接命中预期规则与具体出口，并有双向通路证据。只读连接链只能证明本地路由选择；上游返回流量仍须单独观察。旧两版可以检查实际域名／IP 规则的命中，但不能据此宣称具备统一版的端口一致性及相邻拒绝保护。

### 步骤四：确认手机侧 IMS／WiFi Calling 状态

在设备支持且测试窗口允许时，开启飞行模式后单独打开 Wi-Fi，排除蜂窝通话回退；双 SIM 手机要确认目标线路。若无法排除蜂窝或另一张 SIM 的数据路径，应记录这一限制，不能仅凭接通认定经过所测 Wi-Fi 路径。

- **iPhone：** 查看控制中心内目标运营商线路的“Wi-Fi”状态，不是普通 Wi-Fi 扇形图标。Apple 将这一状态作为 WiFi Calling 可用的标志。[Apple 使用说明](https://support.apple.com/en-us/108066)
- **Android：** 若设备提供 IMS 状态或诊断信息，核对目标 SIM 已注册，并确认接入为 `WLAN/IWLAN`；只显示“IMS Registered”可能对应蜂窝 IMS。Android 的 IMS 注册属性明确区分 WLAN 和 WWAN。[Android IMS 注册属性](https://developer.android.com/reference/android/telephony/ims/ImsRegistrationAttributes)

诊断入口因机型而异，不套用未经核实的拨号代码。手机不提供底层注册信息时，记录“WiFi Calling 状态可见，底层 IMS 注册日志未取得”，再完成业务测试，不把界面状态改写成已经取得底层日志。

**通过依据：** 目标 SIM 的 WLAN／IWLAN 注册证据，或明确标注层级的厂商 WiFi Calling 状态。UDP 4500 活动、IPsec 建立和保活都不能单独替代这一层证据。

### 步骤五：完成最小业务闭环并恢复

在蜂窝回退已排除、profile 和节点不变的条件下，用系统电话应用完成一次呼出和一次呼入，分别确认接通及双向语音。只使用普通测试号码，不用紧急号码做测试。

需要 SMS 时，分别收、发一条普通短信，排除 iMessage、RCS 或其他互联网消息。语音通过不代表 SMS 通过，两项独立记录；发送成功提示不代替对端实际收到。

**通过依据：** 在已确认的 Wi-Fi 路径上，目标 SIM 呼入、呼出及所需短信业务分别有结果。完成测试后恢复原覆写、实际策略组选择和手机网络设置；若临时启用了日志或独立核心，也恢复日志级别并停止测试实例。重新核对已恢复配置，不能只把文件改回却不重新加载。

## 5. 结果记录与定位

下面是空白记录模板，不代表已经验收。记录中只使用本地别名；不要公开订阅、控制器密钥、电话号码、完整 IMS 标识或原始个人抓包。

| 项目 | 实测记录 |
| --- | --- |
| 时间窗口、手机／SIM 别名、网络路径 | 待填写 |
| 客户端、核心、脚本版本／提交 | 待填写 |
| 实际 profile、源地址范围、节点别名 | 待填写 |
| 空组配置与读回 | 已触发并符合预期／未触发／失败，附证据位置 |
| UDP 500 与 4500 | 分别记录是否观察、命中规则、最终节点及双向流量 |
| 手机 IMS／WiFi Calling 状态 | 记录承载网络与证据层级，不只填“成功” |
| 呼入／呼出、双向语音 | 分别记录 |
| SMS 收／发 | 分别记录；不需要时注明未测试 |
| 测试后恢复 | 记录实际加载配置与选择是否恢复 |

定位时保持证据层级：没有手机连接记录，先查流量路径与可观测性；只有发送没有响应，通路尚未证实；UDP 双向而未注册，继续查手机、SIM／运营商条件及认证证据；已注册但单向音频或 SMS 失败，记录对应业务失败，不回退成笼统的“规则有效／无效”。没有新证据时，不扩大分流规则或开启固定 hosts 回退。
